# Android platform capabilities and constraints (30 October 2026)

Part of the Build with Accessibility for Android handoff pack. This document answers one question: what can an app installed from Google Play or as an APK do, and be allowed to do, when it audits other installed apps for accessibility on the same device? The summary below is what the product plan relies on; the numbered sections that follow are the detailed findings with a source for every claim. API levels were read from the live developer.android.com reference on the research date, which already documents API 37 (Android 17). Items marked unverified need a check during the build.

## Summary for the product

### What the app can do

- **Read the full accessibility tree of any foreground app** through an `AccessibilityService` with `canRetrieveWindowContent` and `FLAG_RETRIEVE_INTERACTIVE_WINDOWS`: text, content description, hint, class, bounds, states, actions (including custom actions and their labels), headings, pane titles, labelled-by links, live regions, collection info, range info, error text, tooltip, traversal hints, touch delegates, and, from API 30, state descriptions and `ExtraRenderingInfo` (text size in px and whether it is sp or dp). Android 16 adds supplemental description, required-field, expanded state and tri-state checked. Compose, Flutter and WebView all publish nodes once any accessibility service is enabled, so our own service is enough.
- **Capture pixels** with `AccessibilityService.takeScreenshot` from API 30 (about three frames a second, per display) and `takeScreenshotOfWindow` from API 34 (lets the capture ignore our own overlay). Pixels feed contrast checks, OCR for text hidden in images, colour sampling, colour-vision simulation and change detection.
- **Reuse Google's rule engine.** The Accessibility Test Framework (ATF, Apache 2.0, version 4.1.1) builds a hierarchy straight from `getWindows()` and runs 14 checks, including the screenshot-based text and image contrast checks and an OCR hook (`OcrEngine`) that ML Kit's on-device text recogniser can implement. ATF has not been updated since March 2024 and has open Compose issues, so the plan vendors it as source and fixes what it misreads.
- **Predict TalkBack's reading order** by porting the Apache 2.0 traversal package from the TalkBack repository (about 2,900 lines depending only on `AccessibilityNodeInfoCompat`), and **approximate what TalkBack will say** per node by porting its role-description and node-text utilities. The output is labelled as a prediction against TalkBack 16.2 rules.
- **Record what actually happens** while the auditor uses TalkBack: our service receives the same events TalkBack does (`TYPE_VIEW_ACCESSIBILITY_FOCUSED`, `TYPE_ANNOUNCEMENT`, window state and content changes, speech state changes on API 33+), independently filtered, so a session transcript and a focus-order trace are possible without touching TalkBack.
- **Switch some test conditions directly:** animation scales through `AccessibilityService.setAnimationScale` (API 33, no extra permission), magnification through the service's magnification controller, and font scale through `Settings.System.FONT_SCALE` after the user grants "Modify system settings".
- **Read device state** that an audit must record: font scale, font weight adjustment (bold text), high-contrast or outline text, colour correction and inversion keys, enabled accessibility services, caption settings, dark theme, animation scales.
- **Inspect the audited app's manifest** once it is visible through a `<queries>` declaration: target SDK, activities with a locked `screenOrientation`, `configChanges`, RTL support, and resources by id.

### What the app cannot do, or must not do

| Constraint | Consequence for the product |
|---|---|
| **Google Play's AccessibilityService policy reserves `isAccessibilityTool` for assistive technology.** An auditor is a developer tool and must take the non-tool path: the Permissions Declaration Form, an in-app prominent disclosure with affirmative consent before the Settings hand-off, documentation of the API use in the listing, and no autonomous actions. Google's Accessibility Scanner and Deque's analyzer are both listed this way. | Build the disclosure screen first; record a video of it for the declaration form; every scan and every settings change is user-initiated. Do not declare the tool flag. |
| **Android 14+ `accessibilityDataSensitive` views and events are dropped for non-tool services.** | Authenticator codes and some banking fields are invisible. Report "elements hidden from non-assistive services" as a count, never guess their content. |
| **`FLAG_SECURE` windows deliver a node tree but no pixels.** `takeScreenshotOfWindow` fails with a secure-window error; display captures show black. Play forbids workarounds except for accessibility tools. | Contrast, OCR and colour tools show "not evaluated (secure window)"; structural checks still run. |
| **Most accessibility settings are hidden `Settings.Secure` keys behind `WRITE_SECURE_SETTINGS`,** which third-party apps obtain only through `adb shell pm grant` or Shizuku. Play prohibits changing user settings without permission. | Default to deep links into Settings for display size, bold text, high contrast, colour correction, inversion, TalkBack and captions. Offer the adb or Shizuku route as an explicit, opt-in "advanced switcher" that acts only on a tap. |
| **Android 13+ restricted settings** block enabling an accessibility service for an app installed from an APK file until the user allows it in App info. | The APK onboarding must explain the "Allow restricted settings" step; the Play build does not need it. |
| **`QUERY_ALL_PACKAGES` needs Play approval and is for search, antivirus, file managers and browsers.** | Use a `<queries>` intent filter for launchable apps plus the package names seen in events. |
| **MediaProjection below API 30** needs a consent prompt per session and shows a persistent chip on Android 15+. | Set `minSdk 30` and skip MediaProjection entirely. |
| **The tree can be stale** and nodes hidden with `importantForAccessibility="no"` are only visible with `FLAG_INCLUDE_NOT_IMPORTANT_VIEWS`. | Call `refresh()` before measuring; set the flag so decorative-but-clickable elements are still found, and mark such nodes as "not important" in results. |
| **ATF's English-only heuristics** (redundant descriptions, unclear link text) and skipped WebView content. | Gate those checks on the audited app's locale; treat web content as "not evaluated, use a web checker". |

### Toolchain and distribution decisions this implies

- Kotlin 2.4.x, Android Gradle Plugin 9.5, Compose BOM 2026.09.00 with Material 3 1.4.0 stable (Material 3 Expressive would require 1.5.0 beta; do not take a beta dependency in version 1), JDK 17.
- `minSdk 30`, `targetSdk 36` (Play requires 36 for new apps and updates from 31 August 2026), `compileSdk 36` (or 37 if the API 37 colour fields are used behind a version check).
- Android 11 and newer covered 88 percent of active devices in October 2026; Android 14 and newer, 56 percent. Features that need API 33, 34 or 36 are gated and reported as "not evaluated on this OS version".

## 1. The AccessibilityService API

### 1.1 What a service can read from another app's node tree

A bound service with `android:canRetrieveWindowContent="true"` receives a tree of `AccessibilityWindowInfo` and `AccessibilityNodeInfo` objects via `AccessibilityEvent.getSource()`, `findFocus()`, `getWindows()` or `getRootInActiveWindow()` (https://developer.android.com/reference/android/accessibilityservice/AccessibilityService, "Retrieving window content"). The table lists each node property an auditor cares about and the API level it arrived.

|---|---|---|

Points that matter for an auditor:

- **Role description** is not a framework property. `AccessibilityNodeInfoCompat.getRoleDescription()` (androidx.core, "Added in 1.1.0") "Gets the custom role description" from the node's extras Bundle (https://developer.android.com/reference/androidx/core/view/accessibility/AccessibilityNodeInfoCompat). Read it through the Compat class; the extras key string was not verified in this pass.
- **ExtraRenderingInfo** gives `getLayoutSize()` (the `LayoutParams` width and height, which may be `MATCH_PARENT` or `WRAP_CONTENT`), `getTextSizeInPx()` and `getTextSizeUnit()`, documented as "the text size unit which type is TypedValue.TYPE_DIMENSION of a TextView, or -1 otherwise", which is how you distinguish `sp` from `dp` text (https://developer.android.com/reference/android/view/accessibility/AccessibilityNodeInfo.ExtraRenderingInfo). It is only populated after `refreshWithExtraData(EXTRA_DATA_RENDERING_INFO_KEY, args)`, which the docs describe as "generally expensive to retrieve, so should only be requested when needed" (AccessibilityNodeInfo page).
- **isAccessibilityDataSensitive (API 34)**: the node getter says "Gets if the node's accessibility data is considered sensitive" and points to `View.isAccessibilityDataSensitive()`. On `View`, `ACCESSIBILITY_DATA_SENSITIVE_YES` means "Only allow interactions from AccessibilityServices with the AccessibilityServiceInfo.isAccessibilityTool() property set to true", and `ACCESSIBILITY_DATA_SENSITIVE_AUTO` (the default) treats a view as sensitive when "this view sets getFilterTouchesWhenObscured()" or "any parent of this view returns true from isAccessibilityDataSensitive()" (https://developer.android.com/reference/android/view/View). On the event side, `AccessibilityEvent.isAccessibilityDataSensitive()` (API 34) is "Whether the event should only be delivered to an AccessibilityService with the AccessibilityServiceInfo.isAccessibilityTool() property set to true" (https://developer.android.com/reference/android/view/accessibility/AccessibilityEvent). In AOSP, `AbstractAccessibilityServiceConnection.clientWantsEventLocked` drops the event when `event.isAccessibilityDataSensitive()` and the service lacks `FLAG_SERVICE_IS_ACCESSIBILITY_TOOL`, a fetch flag set only when `mAccessibilityServiceInfo.isAccessibilityTool()` is true (https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/services/accessibility/java/com/android/server/accessibility/AbstractAccessibilityServiceConnection.java). Practical consequence: a non-tool auditor on Android 14+ cannot see or act on views an app marks sensitive (for example 2FA codes in Google Authenticator, the example quoted by Esper: https://esper.io/blog/android-14-accessibility-security-feature). Apps can also detect the caller via `AccessibilityManager.isRequestFromAccessibilityTool()` (API 34, https://developer.android.com/reference/android/view/accessibility/AccessibilityManager).
- **minDurationBetweenContentChanges (API 34)** returns a `Duration`, "the minimum time duration between two content change events" (AccessibilityNodeInfo page). It is a hint set by the app for live regions and progress bars; an auditor can flag missing throttling on rapidly updating nodes.
- **Actions**: the `AccessibilityAction` constants and levels are: all the classic actions (focus, click, long click, scroll forward/backward, expand/collapse, dismiss, copy/cut/paste, set selection, set text, next/previous at granularity, next/previous HTML element) at 21; `ACTION_CONTEXT_CLICK`, `SCROLL_UP/DOWN/LEFT/RIGHT`, `SCROLL_TO_POSITION`, `SHOW_ON_SCREEN` at 23; `SET_PROGRESS` 24; `MOVE_WINDOW` 26; `SHOW_TOOLTIP`, `HIDE_TOOLTIP` 28; `PAGE_UP/DOWN/LEFT/RIGHT` 29; `IME_ENTER`, `PRESS_AND_HOLD` 30; `DRAG_START/DROP/CANCEL` 32; `SHOW_TEXT_SUGGESTIONS` 33; `SCROLL_IN_DIRECTION` 34 (https://developer.android.com/reference/android/view/accessibility/AccessibilityNodeInfo.AccessibilityAction). Custom actions appear in `getActionList()` as `AccessibilityAction` instances with an app-defined id and label (same page), which lets you audit for unlabeled custom actions.

### 1.2 Windows

- `AccessibilityServiceInfo.FLAG_RETRIEVE_INTERACTIVE_WINDOWS` (API 21): "This flag indicates to the system that the accessibility service wants to access content of all interactive windows. An interactive window is a window that has input focus or can be touched by a sighted user when explore by touch is not enabled. If this flag is not set your service will not receive AccessibilityEvent.TYPE_WINDOWS_CHANGED events, calling AccessibilityService.getWindows() will return an empty list, and AccessibilityNodeInfo.getWindow() will return null." It also requires `canRetrieveWindowContent` (https://developer.android.com/reference/android/accessibilityservice/AccessibilityServiceInfo).
- `getWindows()` is API 21 and `getWindowsOnAllDisplays()` API 30 (AccessibilityService page). `AccessibilityWindowInfo` types: `TYPE_APPLICATION`, `TYPE_INPUT_METHOD`, `TYPE_SYSTEM` (21), `TYPE_ACCESSIBILITY_OVERLAY` (22), `TYPE_SPLIT_SCREEN_DIVIDER` (24), `TYPE_MAGNIFICATION_OVERLAY` (33), `TYPE_WINDOW_CONTROL` (36). Useful getters: `getTitle` 24, `isInPictureInPictureMode` 26, `getDisplayId` and `getRegionInScreen` 30, `getLocales` and `getTransitionTimeMillis` 34 (https://developer.android.com/reference/android/view/accessibility/AccessibilityWindowInfo). The class doc notes "there is no root window", so the screen is "a collection of window trees"; an auditor must iterate `getWindows()` rather than assume one root.
- IME windows are reported as `TYPE_INPUT_METHOD`, which is why ATF's touch-target check applies a 32dp minimum inside IME containers (see section 3).

### 1.4 Screenshots, gestures, global actions

- `takeScreenshot(int displayId, Executor, TakeScreenshotCallback)` is API 30 and requires `android:canTakeScreenshot="true"` (`CAPABILITY_CAN_TAKE_SCREENSHOT`, API 30). The result is a `HardwareBuffer` you wrap with `Bitmap.wrapHardwareBuffer`. Error codes: `ERROR_TAKE_SCREENSHOT_INTERNAL_ERROR` (1), `NO_ACCESSIBILITY_ACCESS` (2), `INTERVAL_TIME_SHORT` (3, "too little time has elapsed since the last screenshot"), `INVALID_DISPLAY` (4) at API 30; `INVALID_WINDOW` (5) and `SECURE_WINDOW` (6, "the window contains secure content", see `FLAG_SECURE`) at API 34 (https://developer.android.com/reference/android/accessibilityservice/AccessibilityService).
- The rate limit is not in the public docs. In AOSP it is the hidden constant `ACCESSIBILITY_TAKE_SCREENSHOT_REQUEST_INTERVAL_TIMES_MS = 333` in `AccessibilityService.java`, enforced per service in `AbstractAccessibilityServiceConnection.takeScreenshot` (https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/core/java/android/accessibilityservice/AccessibilityService.java and https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/services/accessibility/java/com/android/server/accessibility/AbstractAccessibilityServiceConnection.java). So roughly three screenshots per second, per display.
- `takeScreenshotOfWindow(int accessibilityWindowId, ...)` is API 34, recommended "if your target window might be visually underneath an accessibility overlay (from your or another accessibility service)" (AccessibilityService page). This is the right call when your own floating scan button is on screen.
- FLAG_SECURE: the per-window variant fails with `ERROR_TAKE_SCREENSHOT_SECURE_WINDOW`. For display screenshots, Google's Accessibility Scanner help states that for windows declared secure "Accessibility Scanner can't capture an image of the screen or check color contrast" and the windows "appear as a black screen", while other scan results remain readable (https://support.google.com/accessibility/android/answer/6376570). The node tree itself is still exposed; a 2020 analysis notes FLAG_SECURE "DOES NOT protect against attacks using Android's accessibility services" (https://wwws.nightwatchcybersecurity.com/2020/03/23/flag_secure-and-accessibility-services-a11y/). Whether display capture on API 30 to 33 returns black pixels or an error was not verified in source. **Unverified.**
- `dispatchGesture` (API 24, `canPerformGestures`): "Any gestures currently in progress, whether from the user, this service, or another service, will be cancelled" and gestures "may be affected by features such as magnification and explore by touch" (AccessibilityService page).
- `performGlobalAction` (API 16) with `GLOBAL_ACTION_BACK/HOME/NOTIFICATIONS/RECENTS` (16), `QUICK_SETTINGS` (17), `POWER_DIALOG` (21), `TOGGLE_SPLIT_SCREEN` (24), `LOCK_SCREEN` and `TAKE_SCREENSHOT` (28), `ACCESSIBILITY_BUTTON`, `ACCESSIBILITY_BUTTON_CHOOSER`, `ACCESSIBILITY_SHORTCUT`, `ACCESSIBILITY_ALL_APPS`, `DISMISS_NOTIFICATION_SHADE`, `KEYCODE_HEADSETHOOK` (31), `DPAD_UP/DOWN/LEFT/RIGHT/CENTER` (33), `MEDIA_PLAY_PAUSE`, `MENU` (36); `getSystemActions()` lists what the device supports (30). `GLOBAL_ACTION_TAKE_SCREENSHOT` triggers the system screenshot UI, not a bitmap for you.
- Other service-side capabilities worth knowing: `setAnimationScale(float)` (33) "Sets the system settings values that control the scaling factor for animations" with no extra permission (see section 5); `getMagnificationController()` (24) with `setMagnificationConfig` (33); `setAccessibilityFocusAppearance` (31); `attachAccessibilityOverlayToDisplay/ToWindow` (34) for `SurfaceControl` overlays; `setCacheEnabled`/`clearCache` (33); `getInputMethod()` and `FLAG_INPUT_METHOD_EDITOR` (33); `getBrailleDisplayController()` (35) (AccessibilityService and AccessibilityServiceInfo pages).

### 1.5 Several services at once, and who gets which events

- Lifecycle: "Starting an accessibility service is triggered exclusively by the user explicitly turning the service on in device settings" and it stops when the user turns it off or it calls `disableSelf()` (AccessibilityService page). A service cannot enable or disable another service.
- Dispatch: `AccessibilityManagerService.notifyAccessibilityServicesDelayedLocked` iterates every bound service (`state.mBoundServices`) and calls `service.notifyAccessibilityEvent(event)`; each connection then filters in `clientWantsEventLocked` by (a) `isImportantForAccessibility` unless the service set `FLAG_INCLUDE_NOT_IMPORTANT_VIEWS`, (b) `isAccessibilityDataSensitive` unless the service is a tool, (c) the service's `eventTypes` mask and (d) its `packageNames` filter; events other than `TYPE_WINDOW_CONTENT_CHANGED` are coalesced per type for `notificationTimeout` milliseconds (https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/services/accessibility/java/com/android/server/accessibility/AccessibilityManagerService.java and AbstractAccessibilityServiceConnection.java above). So TalkBack and your auditor both receive the same events, independently filtered.
- Touch exploration is a shared mode: "The system will enable touch exploration mode if there is at least one accessibility service that has this flag set" (AccessibilityServiceInfo, `FLAG_REQUEST_TOUCH_EXPLORATION_MODE`). An auditor should not request it, otherwise it changes how the user's TalkBack behaves.
- The `DEFAULT` flag: "Default service is invoked only if no package specific one exists. In case of more than one package specific service only the earlier registered is notified" (same page). Leave it unset.
- `AccessibilityServiceInfo.isAccessibilityTool()` (API 31) "Indicates if the service is used to assist users with disabilities", set with `android:isAccessibilityTool` in the service XML (same page). What it unlocks on-device: access to `accessibilityDataSensitive` nodes and events (API 34, above). What it unlocks on Play: exemption from the prominent disclosure requirement and from the autonomous-action prohibition, and an exemption from the FLAG_SECURE rule (section 2). Declaring it falsely is a Play policy violation.

### 1.6 Known blind spots

- **importantForAccessibility="no"**: hidden unless the service sets `FLAG_INCLUDE_NOT_IMPORTANT_VIEWS` (API 16), which makes "views that are marked as not important for accessibility via View.IMPORTANT_FOR_ACCESSIBILITY_NO or View.IMPORTANT_FOR_ACCESSIBILITY_NO_HIDE_DESCENDANTS" reportable (AccessibilityServiceInfo page). Whether the descendants of a `noHideDescendants` view are also returned with the flag was not confirmed. **Unverified.**
- **Compose**: `AndroidComposeViewAccessibilityDelegateCompat.isEnabled` is `accessibilityForceEnabledForTesting || (isAccessibilityEnabled && enabledServices.isNotEmpty())`, where `enabledServices` comes from `AccessibilityManager.getEnabledAccessibilityServiceList(FEEDBACK_ALL_MASK)`; the comment explains this filters out UiAutomator "which doesn't appear in" the list (https://github.com/androidx/androidx/blob/androidx-main/compose/ui/ui/src/androidMain/kotlin/androidx/compose/ui/platform/AndroidComposeViewAccessibilityDelegateCompat.android.kt). So Compose only publishes `AccessibilityNodeInfo` when at least one real service is enabled; an enabled auditor service is enough. Compose nodes are virtual nodes whose class names are often generic (ATF's `ClassNameCheck` exists for this) and ATF has open Compose issues (section 3).
- **Flutter**: the Android `AccessibilityBridge` tells the framework to enable semantics when `AccessibilityManager.isEnabled()` is true (`accessibilityChannel.onAndroidAccessibilityEnabled()`), and `sendAccessibilityEvent` returns early when it is false (https://github.com/flutter/flutter/blob/master/engine/src/flutter/shell/platform/android/io/flutter/view/AccessibilityBridge.java). Flutter's own guidance is that "The framework only generates semantics when asked to do so by the platform" (https://forum.itsallwidgets.com/t/flutter-web-doesnt-build-semantics-nodes-for-performance-reasons/4656, secondary). Again, an enabled auditor suffices.
- **WebView**: Chromium's `WebContentsAccessibilityImpl` "will not do anything until an accessibility service is active and queries the system", "sets a specific AXMode based on the services that are running" (for example only form nodes for a password manager), filters dispatched events to the types running services requested, and tears the engine down when no service is running (https://chromium.googlesource.com/chromium/src/+/HEAD/docs/accessibility/browser/android.md). WebView content arrives as virtual nodes under a `WebView` node; ATF's `SpeakableTextPresentCheck` and `UnexposedTextCheck` skip web content (`RESULT_ID_WEB_CONTENT`). Audit web content with a web-specific ruleset or treat it as out of scope.
- **Unity**: Unity 6's Accessibility module maps its own `AccessibilityHierarchy` to Android nodes (a role becomes "an AccessibilityNodeInfo with className = android.widget.Button") on Android 8.0+, but only if the game builds that hierarchy (https://docs.unity3d.com/Manual/accessibility/module-intro.html and https://docs.unity3d.com/kr/current/Manual/mobile-accessibility.html). Games that do not opt in expose a single opaque surface. **Unreal: no source found; unverified.**
- **FLAG_SECURE**: nodes readable, pixels not (above). Contrast and OCR checks degrade to "not evaluated" for those windows.
- Stale trees: "It is also possible for a node to contain outdated information because the window content may change at any time" (AccessibilityService page). Call `refresh()` before measuring.

### 2.3 Reading of the policy for this product

An app that audits other apps is a developer tool, not a tool whose "primary purpose" is supporting people with disabilities, so by the plain text it is not eligible for `isAccessibilityTool`. That means: complete the non-tool declaration, show the separate in-app disclosure with affirmative consent before sending the user to Settings, document the API use in the listing, keep every action user-initiated (a scan button is "deterministic, rule-based"), and never bypass FLAG_SECURE. It also means accepting the Android 14+ `accessibilityDataSensitive` blind spot, which is small in practice (banking and authenticator screens). Screen capture via the accessibility API or MediaProjection is personal data under the User Data policy and belongs in the same disclosure and in the Data safety form.

### 3.1 Building a hierarchy from a service

### 3.4 How screenshots and OCR feed the checks

- `TextContrastCheck` reads `parameters.getScreenCapture()`, crops the view bounds and builds a `ContrastSwatch` (`utils/contrast/ContrastSwatch`), optionally with `getEnableEnhancedContrastEvaluation()` for multi-colour foregrounds; required ratio is 3.0 for large text and 4.5 otherwise (`isLargeText`). Without a screenshot it falls back to the declared text and background colours, which a service cannot obtain from `AccessibilityNodeInfo` before API 37, where `ExtraRenderingInfo` gains `getTextColor`, `getBackgroundColor` (only "if it is a single color"), `getHintTextColor`, `getLinkTextColor` and `getAlpha` (https://developer.android.com/reference/android/view/accessibility/AccessibilityNodeInfo.ExtraRenderingInfo). ATF 4.1.1 predates API 37 and does not read these, so inside a service the screenshot heuristic is the real path on every supported OS version; on Android 17 devices you can run your own exact WCAG ratio from the reported colours as a second opinion.
- `ImageContrastCheck` works purely on the screenshot (`RESULT_ID_NO_SCREENCAPTURE` otherwise), with a 0.01 tolerance against 3.0.
- `UnexposedTextCheck` consumes `parameters.getOcrResult().getTexts()` (`ocr/OcrResult`, `ocr/TextComponent`) and matches text components to view bounds. `OcrEngine` is a one-method interface: `OcrResult detect(Image screenshot)`. There is no bundled implementation; pair it with ML Kit (section 6).

### 3.5 Known limitations and open issues

Open issues include "Jetpack compose compatibility" (#40, 2021), "ATF skips some Compose elements when AndroidView is present in the same hierarchy" (#87, 2026), "SpeakableTextPresentCheck skipped on Compose IconButton" (#92, 2026), "TextContrastCheck does not run on TextView with Compose Origin" (#76), "TouchTargetSizeCheck for button covered by snackbar" (#91), "Gradle Module Metadata not published" (#80), "4.0.0 is published but there are no release notes" (#50), and two long-standing requests for a custom touch target size (#24, #55; the `Parameters` API now exists). The repo has had no code push since April 2024 (GitHub API `pushed_at` 2024-04-03). English-only heuristics (`RedundantDescriptionCheck`, `LinkPurposeUnclearCheck`) and skipped web content are structural limits.

## 5. Changing device test conditions programmatically

For a self-contained flow, `libadb-android` pairs from inside your app with `AdbConnectionManager.getInstance().pair(host, port, pairingCode)`, Android 11+ only, with the user typing the pairing code from Developer options (https://github.com/MuntashirAkon/libadb-android). Play policy does not address Shizuku explicitly; the relevant constraints are the Accessibility API clause on changing settings without permission and the Device and Network Abuse clause on circumventing sandbox protections (https://support.google.com/googleplay/android-developer/answer/9888379). Ship the Shizuku and adb paths as an opt-in "Advanced: test-condition switcher" with the deep links as the default, and expect a reviewer question. **Risk assessment, not verified policy.**

**Platform test conditions to cover.** Android 14 raised font scaling to 200% with a non-linear curve ("large text doesn't scale at the same rate as smaller text"; "the scaledDensity field is no longer accurate") (https://developer.android.com/about/versions/14/features). Android 15 added HID Braille display support in TalkBack (https://developer.android.com/about/versions/15/features). ## 6. Other building blocks

### 6.1 ML Kit text recognition v2 (OCR for UnexposedTextCheck and image text)

Two install paths: unbundled `com.google.android.gms:play-services-mlkit-text-recognition:19.0.2` ("Model is dynamically downloaded via Google Play Services", "About 260 KB size increase per script architecture", "Might have to wait for model to download before first use") and bundled `com.google.mlkit:text-recognition:16.0.1` ("Model is statically linked to your app at build time", "About 4 MB size increase per script per architecture", "Model is available immediately"); Chinese, Devanagari, Japanese and Korean recognisers are separate artifacts; "Real-time on most devices for Latin script library" (https://developers.google.com/ml-kit/vision/text-recognition/v2/android). The page's "Before you begin" says "This API requires Android API level 23 or above" (its summary block says 21; use 23). The bundled path works offline. Licence: ML Kit is proprietary, under the ML Kit Terms: "ML Kit APIs run on-device", "you may not reverse engineer", "processing of the input data ... fully happens on-device, and ML Kit does not send that data and the resultant outputs to Google servers", but "The ML Kit APIs also send metrics about the performance and utilization of the APIs in your app to Google" and "You are responsible for informing users of your app about Google's processing of ML Kit metrics data" (https://developers.google.com/ml-kit/terms). Implement ATF's `OcrEngine.detect(Image)` by converting the screenshot to an `InputImage` and mapping `Text.TextBlock/Line/Element` bounding boxes to `TextComponent`s.

### 6.2 MediaProjection (screenshots before API 30)

MediaProjection (API 21) is the only pixel source below API 30. "Your app must request user consent before each media projection session. A session is a single call to createVirtualDisplay()." On Android 14+ `createVirtualDisplay()` throws `SecurityException` if the consent `Intent` or the `MediaProjection` instance is reused, and apps targeting 14 "must include a permission declaration for the mediaProjection foreground service type" (`FOREGROUND_SERVICE_MEDIA_PROJECTION`); on Android 15 QPR1+ "a status bar chip that is large and prominent alerts users to any in-progress screen projection" (https://developer.android.com/media/grow/media-projection). FLAG_SECURE content is excluded by definition ("prevent the data from appearing in screenshots", Device and Network Abuse page). Because of the per-session consent prompt and the chip, MediaProjection is a poor fit for repeated scanning; use it only as the sub-API-30 fallback, or set `minSdk 30`.

### 6.3 Reading other apps' manifests and resources

- `PackageManager.getInstalledApplications`, `getPackageInfo`, `getApplicationInfo`, `getActivityInfo` (API 1) are filtered for apps targeting API 30+: "the system filters this information by default ... To view other packages, declare your app's need for increased package visibility using the <queries> element", and `QUERY_ALL_PACKAGES` "is subject to approval" on Play (https://developer.android.com/training/package-visibility). The documented approach for an app that needs to list launchable apps is a `<queries>` intent filter (ACTION_MAIN with CATEGORY_LAUNCHER) rather than the permission (https://developer.android.com/training/package-visibility/declaring; **pattern not quoted in this pass**). Package names observed in `AccessibilityEvent.getPackageName()` can be queried only if they are visible under those rules.
- Useful fields once a package is visible: `ApplicationInfo.targetSdkVersion` (API 4), `minSdkVersion` (24), `compileSdkVersion` (31), `FLAG_SUPPORTS_RTL` (17), `sourceDir` and `publicSourceDir` (1) (https://developer.android.com/reference/android/content/pm/ApplicationInfo); `ActivityInfo.screenOrientation` and `configChanges` with `CONFIG_FONT_SCALE` (1), `CONFIG_DENSITY` (17), `CONFIG_FONT_WEIGHT_ADJUSTMENT` (31) (https://developer.android.com/reference/android/content/pm/ActivityInfo). `resizeableActivity` has no public `ActivityInfo` field (`resizeMode` is hidden). **Unverified beyond the absence on the reference page.**
- Compiled resources: `PackageManager.getResourcesForApplication(String)` (API 1) returns a `Resources` for a visible package, so a `getViewIdResourceName()` such as "pkg:id/name" can be resolved with `getIdentifier` and strings or dimensions read directly. For raw parsing of `base.apk` (resources.arsc and binary XML, including `android:resizeableActivity`), ARSCLib is a pure Java library on Maven Central (`io.github.reandroid:ARSCLib`) "developed based on AOSP structure of androidfw/ResourceTypes.h" (https://github.com/REAndroid/ARSCLib). Whether `publicSourceDir` is readable from another app's process on current Android was not confirmed. **Unverified.**

### 6.4 Play Console pre-launch report

The pre-launch report installs the bundle on lab devices, crawls it "for several minutes" and reports "Stability, Performance, Accessibility, and Screenshots" (https://support.google.com/googleplay/android-developer/answer/7002270). Accessibility findings are split into "Content labeling: Elements in your app that are labelled incorrectly for screen readers. Touch target size: Elements in your app that don't meet the recommended touch target size. Implementation: Layout issues that can make your app difficult to use for users with motor impairments. Low contrast: Low contrast color issues in your app." with screen clusters, example screenshots and a recommendation (https://support.google.com/googleplay/android-developer/answer/9844487). These are the Accessibility Scanner (ATF) categories, so your on-device results can be mapped one-to-one for developers who already see them in Play Console.
